# 06. 미결정 / Open Questions

본 문서는 멀티테넌트 도입과 연동된 미결정 사항을 모은다. 각 항목은 **결정자**, **결정 시점**, **결정 시까지의 기본값(잠정)** 을 명시한다.

---

## A. 사용자 데이터의 멀티 테넌트 공유

### A1. 동일 사용자의 면허번호가 수협마다 다른 경우

- 강구항에서는 `M-201`, 포항에서는 `B-340` 으로 발급 — Membership 단위로 분리 저장 (이미 결정, `01-domain-model.md`)
- **Open**: 사용자 화면 표시 시 어느 면허를 보여줄지
  - 잠정: active tenant 의 면허만 표시
- **결정자**: 제품 운영
- **결정 시점**: Phase 4 UX 디자인 단계

### A2. 사용자 마스터 정보 변경 권한

- User 의 `name`, `email`, `phone` 은 글로벌 자산
- **Open**: 변경 요청을 어느 Tenant Admin 이 승인? Platform Admin 만 가능?
  - 잠정: User 본인 + Platform Admin 만 변경 가능, Tenant Admin 은 Membership 의 `license_no`, `status` 만 관리
- **결정자**: 컴플라이언스
- **결정 시점**: Phase 2 IAM 설계 확정 전

### A3. 선박 마스터의 글로벌 vs Tenant 분리

- `01-domain-model.md` 에서 Tenant 분리 권고
- **Open**: 같은 어선이 여러 위판장에 출하할 경우 데이터 중복 문제
  - 잠정: Tenant 분리. 향후 글로벌 vessel registry 도입 시 양방향 매핑 테이블 추가
- **결정자**: 도메인 전문가 (수산물 유통 경험자)
- **결정 시점**: Phase 1 데이터 모델 확정 전

## B. 정책 데이터 — 수협 간 차이 처리

### B1. 수수료율 차이가 통합 정산 표시에 미치는 영향

- 다중 소속 중매인의 "내 정산 통합 보기" 화면에서 Tenant 마다 수수료율이 다름
- **Open**: 통합 보기에서 합산 시 수수료를 어떻게 표시할지
  - 잠정: Tenant 별로 그룹핑하여 표시, 통합 합계는 "수수료 별도" 라벨
- **결정자**: 제품 운영
- **결정 시점**: Phase 4 UX 단계

### B2. 어종 코드 표준의 출처

- 공유 마스터 `fish_species` 가 따를 외부 표준
- **Open**: 수협중앙회 표준 / KOSIS / 자체 정의 중 선택
  - 잠정: 자체 정의 + 향후 외부 표준 도입 시 매핑 컬럼 추가
- **결정자**: 도메인 전문가
- **결정 시점**: Phase 1 시드 데이터 작성 전

### B3. 박스/마리 환산 중량의 단위 정의

- 요구사항 v0.3 § 7: "표준 박스 중량/마리 평균 중량"
- Tenant 별로 다르며 어종마다도 다름
- **Open**: 환산표의 입력 단위 — 박스당 kg, 마리당 g 등
  - 잠정: `{어종: {박스: kg값, 마리: g값}}` JSONB 구조. 정산 시 자동 환산
- **결정자**: 수협 현장 담당자 (수협 Admin 설정 UI 와 일치)
- **결정 시점**: Phase 3 수협 설정 UI 확정 전

## C. 데이터 보존·법적 요건

### C1. 법적 보존 기간

- 요구사항 § 5: "낙찰가·입찰 이력은 분쟁 대비 영구 보존"
- 사용자 PII 의 보존 기간은 별도
- **Open**: 정확한 법정 보존 기간 (수산물 유통 관련 법령, 전자입찰 관련 규정)
  - 잠정: 거래 기록 5년, 감사 로그 영구, 사용자 PII 는 마지막 거래 후 5년
- **결정자**: 법무 자문
- **결정 시점**: Tenant `archived` 자동 처리 정책 도입 전

### C2. Tenant 아카이브 후 데이터 익명화

- 아카이브 후에도 분쟁 대비 보존하지만 PII 는 익명화 가능
- **Open**: 익명화 범위 — 이름·전화는 마스킹, 면허번호는 유지 등
  - 잠정: 보존 기간 종료 후에만 자동 익명화, 그 전엔 원본 유지
- **결정자**: 법무 + 컴플라이언스
- **결정 시점**: 첫 Tenant 아카이브 발생 전

## D. 운영·과금

### D1. 셀프 등록의 미래 허용 여부

- `03-tenant-lifecycle.md`: 현재는 Platform Admin 직접 생성만
- **Open**: 영업 확장 시 셀프 신청 양식 도입할지
  - 잠정: 도입 안 함. 신청 페이지에서 영업팀 연락처 노출만
- **결정자**: 사업 전략
- **결정 시점**: 가입 수협 5개 이상 시 재검토

### D2. SLA 및 과금 모델

- Tenant 별 거래량·사용량에 따른 과금
- **Open**: 정액(월 구독) vs 거래량 비례 vs 혼합
  - 잠정: 미정 — 초기는 무과금 파일럿
- **결정자**: 사업 전략
- **결정 시점**: 정식 출시 전

### D3. 회계 시스템 연동의 수협별 차이

- 요구사항 § 7: "수협 회계/정산 시스템 연동 가능 여부, API 스펙"
- 각 수협마다 회계 시스템이 다를 수 있음
- **Open**: 어댑터 패턴으로 Tenant별 회계 어댑터 선택 vs 표준 ERP 1개 강제
  - 잠정: 어댑터 패턴, Tenant 설정에 `accounting_adapter: 'suhyup_api_v1'` 같은 식으로
- **결정자**: 시스템 아키텍처
- **결정 시점**: Phase 3 수협 설정 확정 전

## F. 역할별 화면 정책 (`roles/` 도출)

`design/roles/` 의 각 역할 문서를 작성하는 과정에서 추가로 드러난, Tenant 단위 정책 결정이 필요한 항목.

### F1. 재개찰 정책 표준

- `roles/02-operator.md`: 분쟁 발생 시 Operator가 신청, Admin 승인 후 재개찰
- **Open**: 재개찰 횟수 제한 (1회만 vs 무제한), 승인 주체 (Admin 단독 vs 위원회), 시한 (낙찰 후 N시간)
  - 잠정: 회차당 1회, Admin 단독 승인, 정산 확정 전까지만
- **결정자**: 제품·운영
- **결정 시점**: Phase 3 구현 전

### F2. 면허 만료 알림 단계

- `roles/01-suhyup-admin.md`: 7/3/1일 전 알림
- **Open**: 알림 단계를 Tenant 별로 조정 가능하게 할지 vs 글로벌 고정
  - 잠정: 글로벌 고정 (7/3/1일)
- **결정자**: 제품
- **결정 시점**: Phase 3 수협 설정 UI 확정 전

### F3. 패찰 시 낙찰자 노출 정책

- `roles/04-broker.md`: 패찰 카드에 낙찰가와 낙찰자가 표시되도록 mockup 작성
- **Open**: 낙찰자 노출 — 익명 vs 면허번호 vs 이름까지. Tenant 정책으로 분리?
  - 잠정: 면허번호만 노출 (이름·연락처 비공개). Tenant 별로 익명 모드 토글 옵션
- **결정자**: 제품 + 컴플라이언스
- **결정 시점**: Phase 3 수협 설정 항목 확정 전

### F4. 입찰 수정 횟수 제한

- `roles/04-broker.md`, Tenant 설정 `bid_modification_allowed`
- **Open**: 허용 시 횟수 제한 (무제한 vs N회) 도 정책에 포함할지
  - 잠정: 무제한 (bid_modification_allowed=true 면 마감 전까지 자유 수정)
- **결정자**: 제품·운영
- **결정 시점**: Phase 3 전

### F5. 이의 제기 시한 (선주)

- `roles/05-shipper.md`: 출하 상세에서 "이의 제기"
- **Open**: 시한 — 낙찰 후 N시간 이내 vs 다음 정산 확정 전 vs 정산 후 X일 이내
  - 잠정: 낙찰 후 24시간 이내, 단 정산 확정 전이면 시한과 무관하게 허용
- **결정자**: 제품·법무
- **결정 시점**: Phase 3 전

### F6. 작업조(squad) 모델

- `roles/06-union.md`: "본인 소속 작업조의 작업량" 통계
- **Open**: Tenant 내 작업조 데이터 구조 — 별도 엔티티 vs Union Membership 의 metadata 컬럼
  - 잠정: Union Membership 에 `squad_code` (text) — 본격적 작업조 관리는 추후
- **결정자**: 도메인 (노조 운영자)
- **결정 시점**: 첫 노조 사용자 활성화 전
